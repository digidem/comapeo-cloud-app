# Tile proxy edge rate limiting

`GET https://app.comapeo.cloud/api/tiles` is used by SMP downloads to proxy approved tile providers. The Pages Function keeps its existing best-effort in-memory `5000 requests / 60 seconds / IP` limiter as defense-in-depth, but that limiter is scoped to individual Cloudflare isolates and is not distributed abuse protection.

The production control is a **zone-level Cloudflare rate limiting rule** in the `http_ratelimit` phase. It is deliberately limited to the production host, `GET`, and the exact `/api/tiles` path. No other `/api/*` endpoint is in scope.

Cloudflare rate limiting is practical distributed abuse mitigation, not exact globally serialized quota accounting. Cloudflare maintains rate counters per data center, and `cf.colo.id` is therefore an explicit mandatory API characteristic alongside `ip.src`.

## Safety contract

Do not copy the application-level `5000/60s` number into the edge rule. The enforced threshold must come from representative legitimate SMP downloads. The repository tooling refuses enforcement unless the measurement report contains both a small and a large sample, the configured threshold is above the observed legitimate burst, and the operator explicitly confirms that non-blocking false-positive validation has been completed.

Do not add KV or Durable Objects for this rate limit. The edge rule is the intended distributed-abuse layer; exact globally serialized quota accounting is a non-goal.

## 1. Capture representative legitimate downloads

Capture network HAR files from the real application flow on `https://app.comapeo.cloud` using a normal browser profile and normal field-representative connectivity. Do not run an artificial request flood.

Capture at least:

1. **Small:** a small area and modest zoom range representative of a quick field map download.
2. **Large:** a materially larger area and/or higher zoom range representative of the upper end of legitimate use that the product supports.

For each run:

1. Open browser DevTools **Network**.
2. Enable **Preserve log** and clear previous requests.
3. Start the SMP download from the normal UI and let it finish.
4. Export the request log as HAR.
5. Record the map area, maximum zoom, network conditions, browser/device, completion result, and whether the download was intentionally retried.

The HAR parser counts only requests whose host is exactly `app.comapeo.cloud`, whose method is exactly `GET`, and whose path is exactly `/api/tiles`. Requests to staging, preview deployments, or other `/api/*` endpoints are excluded.

HAR files may contain URLs, cookies, and headers. Treat them as operational artifacts: review/redact them as appropriate and **do not commit raw HAR files** to the repository.

## 2. Build the measurement report

```bash
npm run ops:tile-rate-limit -- measure \
  --small /secure/path/small.har \
  --large /secure/path/large.har \
  --output /secure/path/tile-rate-limit-measurement.json \
  --host app.comapeo.cloud \
  --period 60 \
  --safety 1.5
```

The report records request counts, duration, maximum request count observed in the rolling period, the overall legitimate maximum, and a recommended threshold. The default recommendation is the observed maximum multiplied by `1.5` and rounded up to the next ten requests. This is a starting point for observation, not permission to enforce automatically.

Repeat samples if the large flow is not representative, the connection was interrupted, or concurrent downloads are a legitimate expected use case. Prefer the highest credible legitimate burst when setting the threshold.

## 3. Render and review the proposed rule

```bash
npm run ops:tile-rate-limit -- render \
  --report /secure/path/tile-rate-limit-measurement.json \
  --mode observe
```

`--mitigation-timeout SECONDS` controls Cloudflare's mitigation timeout and defaults to the measurement report window. The script validates the value locally before any Cloudflare mutation; supported values are `0`, `10`, `60`, `120`, `300`, `600`, `3600`, and `86400` seconds.

The rule expression must remain exactly equivalent to:

```text
http.host == app.comapeo.cloud
AND http.request.method == GET
AND http.request.uri.path == /api/tiles
```

The API representation generated by the script uses:

```text
(http.host eq "app.comapeo.cloud" and http.request.method eq "GET" and http.request.uri.path eq "/api/tiles")
```

and rate characteristics `cf.colo.id` plus `ip.src`.

Cloudflare plan capabilities vary. In particular, the available matching fields and non-blocking `log` action depend on the zone plan. If Cloudflare rejects the exact expression or `log` action, **do not weaken the scope and do not switch directly to blocking**. Use Cloudflare Request Rate Analysis / Security Analytics as the closest available non-blocking validation mechanism, or upgrade the plan so the exact production-host + method + path rule can be expressed.

## 4. Observe before enforcing

Where the zone supports a rate-limiting `log` action, apply the observation rule with credentials that have the required Zone WAF / Rulesets permissions:

```bash
CLOUDFLARE_API_TOKEN=... npm run ops:tile-rate-limit -- apply \
  --report /secure/path/tile-rate-limit-measurement.json \
  --mode observe \
  --zone comapeo.cloud
```

The script discovers the active `comapeo.cloud` zone, reads the `http_ratelimit` entry-point ruleset, and upserts only the rule whose stable reference is `comapeo-cloud-app-tiles-rate-limit`. New rate-limiting rules are appended to the end of the phase as required by Cloudflare.

During observation:

- Repeat both small and large legitimate SMP downloads.
- Check Cloudflare Security Events / Security Analytics / Request Rate Analysis for the proposed threshold.
- Confirm the rule does not match other hosts, methods, or `/api/*` endpoints.
- Check for legitimate clients that share a public IP or perform concurrent downloads.
- If legitimate traffic would exceed the threshold, raise the threshold and repeat observation.

If the plan does not support `log`, use the same expression and threshold in Cloudflare's non-blocking analytics tooling and record the would-block result before enforcement.

## 5. Enable enforcement

Only after the observation period has shown no legitimate false positives:

```bash
CLOUDFLARE_API_TOKEN=... npm run ops:tile-rate-limit -- apply \
  --report /secure/path/tile-rate-limit-measurement.json \
  --mode enforce \
  --zone comapeo.cloud \
  --confirm-false-positive-validation
```

The script refuses enforcement when:

- either the small or large measurement is missing;
- the report target is not production `GET /api/tiles`;
- the report period differs from the configured period;
- the threshold is less than or equal to the observed legitimate maximum; or
- `--confirm-false-positive-validation` is omitted.

An explicit higher threshold can be supplied with `--threshold N` after observation justifies it.

If a different supported mitigation timeout is required, pass `--mitigation-timeout SECONDS`; otherwise it defaults to the measurement window from the report.

## Client-visible behavior

The enforced edge rule returns HTTP **429** with `Content-Type: text/plain` and:

```text
Tile download rate limit exceeded. Retry after a short delay.
```

The Pages Function's existing isolate-local fallback limiter also returns 429. A 429 during an SMP download should therefore be treated as a transient rate-limit failure: stop/retry after a short delay rather than repeatedly issuing more tile requests.

## Operational visibility

Inspect the managed rule without changing it:

```bash
CLOUDFLARE_API_TOKEN=... npm run ops:tile-rate-limit -- status --zone comapeo.cloud
```

The status output includes `managedRuleCount` and `duplicateManagedRules`. Normal operation has exactly one managed rule. If multiple rules have the stable managed reference, `apply` fails closed instead of updating an arbitrary match. Resolve the duplicate configuration before applying a new threshold or mode.

For repository operators who do not have a local Cloudflare token, `.github/workflows/tile-rate-limit-ops.yml` exposes the same `status`, `observe`, `enforce`, and `disable` operations through GitHub Actions using the repository Cloudflare secret. Enforcement still requires an explicit false-positive-validation confirmation. The production baseline currently used by that workflow is `ops/tile-rate-limit/production-baseline-2026-08-14.json`; replace it only after collecting and reviewing a newer representative small + large production measurement.

Operational checks after enforcement:

- Cloudflare Security Events / rate-limit analytics for rule matches and mitigations;
- SMP download completion/error reports from the application;
- unexpected 429 reports from users;
- changes in legitimate peak request rates after SMP download implementation changes.

Re-profile small and large downloads after changes that materially alter tile concurrency, buffering, global-overview behavior, or supported maximum zoom.

## Rollback / disable

The fastest repository-supported rollback is to disable only this managed rule:

```bash
CLOUDFLARE_API_TOKEN=... npm run ops:tile-rate-limit -- disable --zone comapeo.cloud
```

Then verify:

```bash
CLOUDFLARE_API_TOKEN=... npm run ops:tile-rate-limit -- status --zone comapeo.cloud
```

The rule should report `enabled: false`. The disable command disables every rule with this managed reference before reporting success, and `status` exposes the number of matching rules for cleanup. This does not remove or modify unrelated rate-limiting rules. The Pages Function's application limiter remains active as defense-in-depth.

The same rule can also be disabled in Cloudflare Dashboard under **Security / WAF / Rate limiting rules**. If the edge rule causes a production incident, disable it first, confirm `/api/tiles` resumes normal behavior, and investigate/tune before re-enabling.

## Cloudflare permissions and plan notes

The token used for `apply`, `status`, or `disable` must be able to list the `comapeo.cloud` zone and read/write the zone Rulesets/WAF configuration. Keep the API token in a secret store; never place it in the measurement report, command history committed to Git, or repository files.

Cloudflare plan limits determine which request fields, periods, characteristics, and actions are available. A failure caused by plan restrictions is a deployment blocker for this exact rule, not a reason to broaden the match or introduce application-side distributed state by default.
