# QA — Issues #306 + #308: mobile map overlay stacking

## Scope

Validate that app-owned controls render and receive pointer input above MapLibre on mobile while normal map interaction remains available, without changing desktop layout.

This covers:

- #306 — Alerts map inline point-selection bar (`Back to form`) while selecting a point on mobile.
- #308 — Map authoring draw controls (`Cancel`, `Set this area`, draw frame, and `Undo`) on mobile.
- Regression safety for ordinary map pan/zoom and desktop layouts.
- Empty-state map scrims in Alerts/Data remain below app-owned basemap and active-map controls after MapLibre isolation.

## Prerequisites

- Use the PR preview/staging deployment built from the final PR head SHA.
- Test at a mobile viewport around 390×844 (or a physical mobile browser) and desktop at 1440×900.
- Have at least one project selected. For Alerts, the project may contain zero or more alerts.

## Automated verification

Run the implementation-specific helper from the repository root:

```bash
./scripts/qa/issues-306-308.sh
```

The helper runs the focused unit suite, TypeScript validation, both Chromium stacking regressions, and a production build. Expected: every command exits 0. The Playwright tests assert browser hit-testing at multiple interior points of each control and minimum 44×44px interactive targets, including a synthetic high-z MapLibre descendant that reproduces the stacking-context failure deterministically.

## Mobile QA — Alerts map (#306)

1. Open **Alerts** in map view at approximately 390×844.
2. Tap **Add Alert**.
3. In the inline sheet, tap **Select on map**.
4. Confirm the inline sheet hides and the bottom instruction bar appears with **Back to form**.
5. Confirm the complete bar is visible above the map with no clipping or occlusion.
6. Tap **Back to form**. Confirm the alert form reopens immediately.
7. Tap **Select on map** again, then tap an unobstructed point on the map.
8. Confirm the alert form reopens with the selected point reflected in the geometry picker.
9. Repeat normal map pan/zoom gestures outside the bottom bar.

Expected:

- The bottom bar and **Back to form** are always in front of the map and tappable.
- **Back to form** has at least a 44×44px hit target.
- Tapping the map still selects a point after entering selection mode.
- Normal map gestures are not blocked outside app controls.

Failure conditions: any app control appears behind map content, requires repeated taps, is clipped off-screen, or map point selection/gestures stop working.

## Empty-state map-control regression QA

1. In **Alerts** map view, use a project that contains alerts but no valid alert geometry so **No alerts with location to show on the map** is visible.
2. Confirm the dimmed empty-state scrim covers the map content while the **Basemap** switcher remains visible above it and opens on the first tap/click.
3. If an active-map badge is present, confirm the badge remains visible above the scrim.
4. Repeat the same check in **Data** map view with observations that have no valid latitude/longitude.

Expected: the empty-state scrim blocks/dims the map surface but does not cover or intercept app-owned basemap or active-map controls.

Failure conditions: the scrim paints above the basemap switcher/active-map badge, or clicking those controls is intercepted by the scrim.

## Mobile QA — Map authoring (#308)

1. Open **Map** at approximately 390×844 with a project selected.
2. Confirm the **Draw bounds** button is tappable.
3. Tap **Draw bounds**.
4. Confirm the instruction banner, cancel control, dashed draw frame, and **Set this area** button are all fully visible above the map.
5. Pan and zoom the map until the desired area is inside the frame.
6. Tap **Set this area**.
7. Confirm **Map area updated** appears with an **Undo** control.
8. Tap **Undo** and confirm the previous bounds are restored and the status control disappears.
9. Exit draw mode and verify ordinary map pan/zoom still works.

Expected:

- Every draw-mode control receives input on the first tap.
- Interactive controls are at least 44×44px.
- Map movement remains usable for framing while draw mode is active.
- After draw mode ends, ordinary map interaction remains unchanged.

Failure conditions: any control is visually behind the map, pointer input lands on the map instead of the control, Undo is undersized/unreliable, or pan/zoom behavior regresses.

## Desktop regression QA

At approximately 1440×900:

1. Open **Alerts** → map view → **Add Alert**.
2. Confirm the desktop inline creation sheet remains in its existing right-side layout and does not cover unrelated controls incorrectly.
3. Open **Map**, enter and cancel draw mode, then set an area.
4. Confirm desktop drag-to-draw behavior and control placement remain unchanged.

Expected: no visible layout or interaction regression from the pre-change desktop behavior.

## Cleanup / reset

- Cancel any unfinished inline alert creation.
- Use **Undo** if a temporary map area was set during QA, or reload the preview if no persistent save occurred.
- Do not save a temporary authored map unless specifically testing persistence.

## Known limitations

- Firefox/WebKit Playwright runs in this repository do not provide the WebGL behavior required for these mobile MapLibre interaction flows; both issue-specific mobile tests are therefore intentionally skipped off Chromium. Cross-browser regression safety is still covered by the repository-wide CI/E2E suite where applicable.
- The synthetic high-z test fixture is test-only; production behavior is also verified manually on the PR staging deployment.
