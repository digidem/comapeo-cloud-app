# QA Script — Issue #336: Alerts created on the app are sent to the Remote Archive

Issue: #336 — Alerts created on the app are not sent into the Remote Archive
Spec: `docs/superpowers/specs/2026-09-03-issue-336-send-app-alerts-to-archive.md` (canonical; where issue/QA disagree the spec wins)

## Scope

This QA validates that creating an alert from the web app reaches the connected **Remote
Archive** (comapeo-cloud server) instead of only being written to local IndexedDB, and
that the **server-generated** alert is what the app displays afterward (server is the
source of truth). Specifically, for an **archive-backed** selected project
(a project whose row carries a server `remoteId` and an owning archive server with a
token), submitting the Create Alert form:

- issues **exactly one** `POST /projects/{remoteId}/remoteDetectionAlerts` to the owning
  archive with a `createAlertBodySchema`-shaped body (Bearer auth, `Content-Type:
  application/json`);
- **does not** write a transient `sourceType:'local'` alert row;
- after the archive `201` (empty body), (re)fetches the project's alert collection and
  only reports success once an echoed `remoteArchive` server row with the submitted
  geometry/`sourceId` is visible; a bounded wait guards against racing a blind refetch —
  if the echo cannot be confirmed it reports failure, never fake success.

Pure-**local** projects (no owning archive) keep the existing local write untouched
(out of scope for the archive path; a local-only alert is not visible to CoMapeo Mobile,
which is the documented limitation motivating the archive-authoritative path).

Out of scope (unchanged): the pull-only sync/reconciliation engine, the `Alert` DB row
schema / any storage-reset behavior, other resource kinds (observations, cases, …), and
the raw `apiClient.createAlert`/`createAlertBodySchema` contract.

## Prerequisites

1. Check out the implementation branch at the candidate SHA; run `npm install`.
2. Start the dev server: `npm run dev` (http://localhost:5173).
3. A reachable archive for the flow, with the project in question synced so its row has a
   server `remoteId` and the owning archive server is connected with a valid token.
   Without a live archive for manual verification, rely on the automated unit coverage in
   `tests/unit/lib/data-layer-alerts-archive.test.ts` (MSW stubs the 201-empty POST and
   the echo GET) for the archive path, and confirm the local-only fallback manually on any
   disconnected/project.
4. Unit gates green before manual QA:
   `NODE_OPTIONS=--localstorage-file=/tmp/x npx vitest run --project=unit tests/unit/lib/data-layer-alerts-archive.test.ts tests/unit/hooks/useCreateAlert.test.tsx tests/unit/lib/data-layer.test.ts tests/unit/screens/CreateAlertScreen.test.tsx tests/unit/screens/AlertsScreen.test.tsx`
   (The `--localstorage-file` Node flag is only needed on runtimes where Node 26's
   experimental global shadows jsdom `localStorage`; on the repo-pinned Node 22 it is
   unnecessary.)
5. A browser that can open browser DevTools → Network.

## Steps and expected results (manual, archive-backed project)

### 1. Create alert → single POST + echo GET to the owning archive

1. Select an **archive-backed** project, open **Alerts**.
2. Open browser Network, then create an alert (Add Alert → either the standalone
   `/alerts/new` form or the inline map Add Alert point/draw).
3. Fill a geometry (point/polygon), a Source ID, and dates; submit.
   - Expected: exactly **one** request `POST
     .../projects/{remoteId}/remoteDetectionAlerts` to the owning archive with HTTP **201**
     (empty body), a Bearer `Authorization` header, and a JSON body containing
     `detectionDateStart`, `detectionDateEnd`, `sourceId` (non-empty), `metadata`, and
     `geometry` (the same payload a manual CLI archive call would send). No
     `sourceType:'local'` alert row is persisted.
   - Expected: after the 201, exactly one follow-up GET of the project's
     remoteDetectionAlerts collection (the echo), then the form reports success and the
     new alert card appears **once** in the Alerts list/map (server docId).
4. Refresh the Alerts screen: the created alert persists (it comes from the archive).
5. Pull the same alert into a separate consumer (e.g. CoMapeo device syncing that archive,
   or a `curl` GET of the alerts collection) and confirm it appears — this is the actual
   issue’s acceptance (CoMapeo Mobile must see the app-created alert).

Failure conditions: if the POST returns non-2xx/network error/403 (auth) → the form shows the
existing "Could not create the alert" copy, stays open, and **no** local row is written; the
alerts list is unchanged.

### 2. Local-only project keeps existing local behavior

1. Select a **local-only** project (no owning archive / no remote Id) and create an alert.
   - Expected: an alert row is written locally and appears in the Alerts list as before
     (no network POST). No error.

## Cleanup / reset

- Created archive alerts are real server records; after QA, remove the test alert from the
  archive (or via its owning project) so subsequent runs observe fresh creation and verify
  the POST-then-GET flow, not deduplication of an existing record.

## Known limitations

- The archive POST returns an empty 201 and the server mints the alert `docId` internally
  and never returns it; the app therefore cannot echo/predict that id and relies on the
  follow-up GET of the collection to surface the canonical row. Echo propagation latency
  shows up as the brief post-submit wait; if the server does not echo within the bounded
  wait the create reports failure (never a phantom success).
- Pure-local projects remain local-only by design and are not visible to CoMapeo Mobile —
  the documented limitation motivating the archive-authoritative path.
- This QA assumes the selected **archive-backed** project row carries its server `remoteId`
  and resolves an owning server with a token (the same ownership source the Categories
  editor and `useApiPresets`/`useApiFields` use). Projects modeled only by `serverUrl`
  without a `remoteId` are treated as local by the current resolve logic and are covered by
  Step 2.
