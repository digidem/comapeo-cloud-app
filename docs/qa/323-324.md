# QA Script — Issues #323 + #324: Worker task yielding and latest-category iteration cleanup

Issues: #323 and #324

## Scope

This QA validates two maintenance changes without changing user-visible product semantics:

1. **#323 — area-calculation worker cancellation:** area methods remain sequential and continue emitting ordered progress/result messages, but the worker now yields to the browser task queue between methods so a newer queued `message` task can update the active request id and stop stale work before it emits more results or `done`.
2. **#324 — latest category-set selection:** selecting the newest time cluster keeps the same membership and original input order while the final membership projection is performed in one pass rather than `.filter().map()`.

Out of scope: changing calculation formulas, coverage presets, category clustering rules, category persistence, worker protocol shapes, or UI styling.

## Prerequisites

1. Use the candidate PR preview/staging deployment for browser QA, or run the candidate SHA locally with `npm run dev`.
2. For Home coverage QA, use a project containing enough point observations to produce the normal five coverage methods.
3. For Categories QA, use a project with at least two time-separated category/preset clusters if available; otherwise rely on the deterministic unit fixtures for cluster separation and ordering.
4. Required automated gates before handoff:
   - `npm test -- tests/unit/lib/area-calculator/worker.test.ts tests/unit/lib/latest-set.test.ts`
   - `npm run lint:types`
   - `npm run lint:eslint`
   - `npm run lint:prettier`
   - `npm run test:coverage`
   - `npm run build`

## Automated acceptance checks

### #323 worker cancellation

Run `tests/unit/lib/area-calculator/worker.test.ts`.

Expected:

- all existing progress/result/error/done ordering tests pass;
- the queued-task regression (`yields to message tasks so a queued newer request cancels stale work`) passes;
- the test models a newer request arriving through `setTimeout(0)`, i.e. a task-queue turn rather than direct concurrent invocation;
- the stale request does not emit `done` and does not emit all five results after the newer request is queued;
- the newer request completes normally.

Failure condition: the old request reaches `done`, emits all five results, the newer request fails to finish, or result/progress ordering changes.

### #324 latest category set

Run `tests/unit/lib/latest-set.test.ts`.

Expected: all cluster-boundary, deleted/invalid timestamp, newest-cluster membership, and original-order preservation cases pass unchanged.

Failure condition: latest-cluster membership changes, deleted/invalid presets reappear, boundary behavior changes, or result order changes.

## Browser / staging QA

### 1. Home coverage calculation smoke

1. Open the PR preview/staging deployment and select a project with point observations.
2. Open Home and wait for coverage calculations to complete.
3. Confirm the coverage calculation completes without a worker error and the normal coverage outputs render.
4. Change a coverage calculation setting/preset repeatedly while calculations are active, including several rapid changes.
5. Confirm the final displayed coverage corresponds to the latest selected settings, the UI does not become stuck in a calculating state, and no stale error/result replaces the latest calculation.
6. Inspect the browser console during the sequence.

Expected: no uncaught worker errors, no stale completion visibly overwrites the latest state, and the final calculation completes normally.

### 2. Categories latest/all behavior

1. Open the Categories editor for a project with multiple category/preset generations when available.
2. Use the Latest view and note the displayed newest cluster and its order.
3. Switch to All and confirm older/non-latest active presets remain available there.
4. Switch back to Latest.

Expected: Latest shows only the newest cluster in its existing input order; All remains unchanged; switching views produces no console/runtime errors.

If staging data has only one category cluster, this manual test can validate the view smoke only; the multi-cluster and order semantics are covered by the deterministic unit suite.

## Regression checks

- Navigate away from Home during/after a calculation and return; no worker/runtime error should appear.
- Refresh Home and Categories; both flows should initialize normally.
- Test at desktop and mobile viewport widths. These changes are not visual, so no visual-baseline update is expected.

## Cleanup / reset

No persistent data needs to be created or changed for these checks. If calculation settings were changed, restore the original preset/settings. Do not modify category data solely for this maintenance QA.

## Known limitations

- The production Home hook currently creates/terminates workers as its effect lifecycle changes, so the precise same-worker queued-message cancellation invariant is most deterministically exercised by the worker unit regression. Browser QA validates that the shipped Worker module and surrounding coverage flow remain healthy under rapid recalculation.
- #324 is intentionally a semantics-preserving iteration cleanup; there is no expected visual difference to inspect.
